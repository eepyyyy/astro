Accuracy & Testing

Getting the Rasi right is not enough. For Jamakkol Prasanam to be useful, the degree-level precision must match reference tools like jamakkol.com. This page tells you exactly what to check and how to debug discrepancies.

The Most Common Mistakes

SymptomLikely CauseFix
Planet in wrong Rasi Forgot set_sid_mode() or using tropical longitudes Always call swe.set_sid_mode(swe.SIDM_LAHIRI, 0, 0) at startup
Sunrise off by hours Passing local time to rise_trans() instead of UTC The jd_start must be a Julian Day in UTC (not IST)
Sunrise off by ~2 minutes Not including the elevation Pass the alt (elevation in metres) parameter to rise_trans()
Udhayam in wrong sign Starting from Sun's degree instead of Rasi boundary Use sun_rasi_index × 30, not sun_longitude
Arudham off by 1 Rasi Using minutes only (not seconds) in the 5-minute rule Use total_seconds = minute * 60 + second, divide by 300
Mandi in wrong sign Kala index is 1-based in some references, 0-based in code Double-check lookup table. Mandi index 0 = first Kala of the day
Rahu appears direct Using swe.MEAN_NODE instead of swe.TRUE_NODE Use swe.TRUE_NODE. Rahu (True Node) is always retrograde

Validation Checklist

Before going live, verify each of these in order:

  • 1
    Check the Sun's position

    Compare your nps["Sun"]["rasi_en"] against any online ephemeris (like astro.com). In August, the Sun should be in Kadagam (Cancer). If it's wrong by ~24°, you forgot the Ayanamsa.

  • 2
    Check sunrise time

    Compare sunrise_ist against a weather app or Google for the same date and city. Should match within ±2 minutes. If it's 5.5 hours off, you passed local time as UTC.

  • 3
    Check Arudham at a known minute

    Test at exactly 14:00:00. Minute = 0, so Arudham should always be Mesham (Aries). Test at 14:05:00 → Rishabham. If this is wrong, your 5-minute logic has a bug.

  • 4
    Compare with jamakkol.com

    Open jamakkol.com, enter a specific time and location, and compare all values with your API output. Start with Arudham (easiest to verify), then Udhayam, then Kavappu.

Quick Sanity Tests

from jamakkol_engine import compute
from datetime import datetime

Chennai = {"lat": 13.0827, "lon": 80.2707, "alt": 6}

# Test 1: Arudham at minute=0 must always be Mesham
r = compute(datetime(2026, 8, 4, 14, 0, 0), **Chennai)
assert r["arudham"]["rasi"] == 0, "Arudham at :00 should be Mesham (0)"
print("✓ Arudham at :00 → Mesham")

# Test 2: Arudham at minute=30 must be Thulaam (6)
r = compute(datetime(2026, 8, 4, 14, 30, 0), **Chennai)
assert r["arudham"]["rasi"] == 6, "Arudham at :30 should be Thulaam (6)"
print("✓ Arudham at :30 → Thulaam")

# Test 3: Ayanamsa must be around 24.2° in 2026
ayanamsa = r["ayanamsa"]
assert 24.0 < ayanamsa < 24.5, f"Ayanamsa {ayanamsa} out of expected range"
print(f"✓ Ayanamsa = {ayanamsa:.4f}° (Lahiri 2026)")

# Test 4: Rahu is always retrograde
rahu = r["nitya_planets"]["Rahu"]
assert rahu["retrograde"] == True, "Rahu must always be retrograde"
print("✓ Rahu is retrograde")

# Test 5: Ketu is exactly 180° opposite Rahu
ketu    = r["nitya_planets"]["Ketu"]
diff_rk = abs((rahu["degree"] - ketu["degree"] + 360) % 360 - 180)
assert diff_rk < 0.01, "Ketu must be 180° from Rahu"
print("✓ Ketu is 180° from Rahu")

print("\nAll tests passed! ✓")

💡 Final tip

The calculation in this library matches jamakkol.com to the degree level for Udhayam, Arudham, and Kavappu. The only area where slight differences can occur is Mandi/Gulika — different practitioners use slightly different Kala assignment tables. If you find a mismatch, check the Kala index table in Mandi & Gulika.
